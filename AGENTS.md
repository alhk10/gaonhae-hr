# Project architecture
- Canonicalize legacy Perth competition event codes at database writes and frontend read boundaries, without changing competitor grades, so merged events remain visible in PDFs, logs and editing.

- Staff slot capacity uses the shared `slotCapacity` weekday and availability helpers, never display-formatted dates as configuration keys, so calendars and branch moves agree on daily limits.

- Resolve invoice PDFs through the saved active template for each invoice's own branch country, never a generic country fallback, so branding and payment details stay accurate after branch changes.
- Public invoice-detail SECURITY DEFINER functions attach only the matched invoice's country template; `/hello` uses its session-validated invoice list to preserve access checks.
- Shared `/access` staff-list presentation uses an `.access-list-shell` container and `.access-list-table` field markers, so rows flow into labelled two-line layouts based on available list width without changing actions or queries.
- `/hello` reusable passport photos and Poom/Dan certificates are private `student-photos` objects, uploaded and previewed only after a server-validated recognized-student chat session; competition forms copy authorized images into each submission and save new profile copies only when the default-on switch remains enabled, so later replacements never alter past entries.
- Convert invoice-edit overpayments through the database function keyed by invoice reference, so the existing invoice reaches zero balance and repeated saves cannot duplicate student credits.- Payroll month adjustments (pro-ration, unpaid/excess annual leave, encashment) come from `payrollAdjustmentsService` and are applied through `computeFullTime` in Payroll Processing, so review, bank and CPF steps always agree.

- `/access` branch passwords may map to several branches (one `access_unlock_passwords` row per branch; `_access_scope` returns a comma list checked with `_scope_has`); the UI keeps one active branch and offers a switcher, so all tabs keep single-branch filtering.
- Duplicate grading payments (same matched student + grading slot) are blocked by a database insert trigger and resolved by staff via credit conversion, so checks can't be bypassed by branch or name spelling.
- Grading, competition and guards submissions auto-verify in a database trigger only when matched and the scanned amount equals the amount due to the cent; existing auto-invoice triggers then create the invoice, so staff and /hello paths share one rule.
- `/hello` checkouts send a stable `client_ref` to `submit_public_chat_invoice`, which returns the existing invoice for a retry and refuses identical items for the same student within 24 hours.

- Every payment insert/update/delete recalculates its invoice via `recalc_invoice_from_payments` (drafts included; pending payments count toward paid), so auto-verified /hello payments never leave invoices showing outstanding.
- Student class attendance lives only in `lesson_bookings` (one row per student/timeslot/date; requested → booked → attended|absent, or rejected), managed through `/access` Attendance RPCs and `/hello` `hello_submit_lesson_request`; a database trigger charges one entitlement lesson per attended/absent mark and refunds it on unmark/delete, so every path agrees on lesson balances.
- Finance is a per-branch running journal in /access (all-branch password only) built live by `access_branch_journal` from payments, cash credit refunds and manual `branch_journal_entries`; the old double-entry ledger/P&L was removed, so never reintroduce posting calls in invoice/payment services; the separate Branch P&L page (`/branch-profit-loss`) is a manual-entry monthly report only.
- Unresolved payment shortages (scanned proof < recorded amount, pending) count only the scanned amount in `recalc_invoice_from_payments`, and only superadmin resolves them via `admin_resolve_payment_shortage`, so invoices never show paid for an underpayment.
- /access staff passwords are managed only via all-branch-password-gated SECURITY DEFINER functions (access_password_*) storing sha256 hashes, so passwords are never readable and branch staff can't alter access.
- Payments auto-verify as a set via `_auto_verify_invoice_payments` (called from the payments sync trigger): when all non-rejected counted amounts equal the invoice total to the cent, pending payments are verified and set to their counted amount, so split payments clear shortages without double counting.
- Poom and Dan are separate grading tracks; Poom→Dan and Dan→Dan conversions happen only through STF conversion products (metadata `conversion_from`/`conversion_to`), checked by `_dan_conversion_check` on invoice lines and mirrored in `src/utils/danConversion.ts`, so grading never silently converts ranks.
- Poom/Dan certificates live in `student_certificates` and are uploaded and scanned only through the `student-certificate` edge function, gated by a staff password scope or a validated /hello session. Approval sets `last_dan_conversion_at` and the student's competition certificate, so wait periods and form auto-fill use verified data.
- Dan > Dan conversion requires the stored `pre_conversion_poom` number to be at least the target Dan (checked in `_dan_conversion_check` and `danConversion.ts`); otherwise the student grades, and passed Dan gradings set `last_dan_conversion_at` so wait periods stay consistent.
- Grading belt outcomes come from the linked fee line "X >> Y" (SQL `_grading_effective_belts`, mirrored in `src/utils/gradingOutcome.ts`); Double adds one belt; combined Foundation lines on one invoice (`_grading_steps`) write one history row per step under a single registration, so each step gets its own certificate.
- GST is always charged on the subtotal after discount (`src/utils/invoiceTotals.ts`); invoice totals display Subtotal > Discount > GST > Total, so printed math matches what is charged.
- Attendance term arrows use the full branch calendar from attendance settings and jump to adjacent term start dates; week-scoped terms cannot navigate across term breaks.
- ANEXT bank alert emails are pulled by the `anext-email-sync` edge function (Gmail connector, pg_cron, DB-stored sync token) into `bank_transactions`; payments are verified only via `reconcile_bank_transaction`/`access_bank_match`, linked through `bank_transaction_payments` (one transfer may verify several payments, each payment at most once) with exact-cent totals, ±1 SGT day and no shortage; auto-match needs a reference match or a remembered family payer (`bank_payer_aliases`, many students per payer), so wrong transfers can't verify payments.
- Term fee status comes from SQL `_term_coverage` (mirrored by `termCoverage` in `src/utils/termFullyPaid.ts`): weeks paid (line quantity, 4 for the 4-week plan) count forward from the term start or a late joiner's first invoice date; a student is paid while today is inside that span, and `_term_payment_status`, `term_payment_statuses` and `student_term_coverage` expose it, so every page agrees.
- Branch-scoped settings RPCs (guards/class pricing, grading slots, studio rental) are thin wrappers that call `_settings_guard(p_password, branch, require_all)` before a revoked `_impl_*` function; company-wide limits need the all-branch password or superadmin, so branch passwords can't change other branches.
- Public catalogue reads use the generated Supabase RPC signature without staff-password arguments, so `/hello` works without an `/access` session.
- Ticking Ready for grading in /access checks term fees via `access_grading_term_fee_status`; staff may set `grading_registrations.fee_override`, which `hello_grading_eligibility` honours, so fee exceptions are explicit and per term.
